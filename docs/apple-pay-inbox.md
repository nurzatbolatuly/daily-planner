# Apple Pay → CashFlow: покупки из Wallet во «Входящие»

Статус: **в работе** — готово: БД (v41), функция `wallet-ingest`, экран «Apple Pay» (ключи) и
«Входящие» (мой расход, валюта, дубли, пачка). Осталось: команда iOS (этап 3, на iPhone) и
«В общие расходы» (этап 7).
Журнал — §15.
Источник правды по этапам — §12 (статусы ⬜/🔄/✅). После каждого этапа обновлять статус здесь,
`instruction.md` и `SKILL.md`.

---

## 1. Задача и границы

**Хочу:** оплатил телефоном/часами → покупка сама появляется в CashFlow, я только подтверждаю.
**Особый случай:** оплатил за всех (кафе, такси, продукты на компанию) → покупка уходит не в мои
расходы целиком, а в «Общие расходы» (туса или Tricount) или в «Оплатил за других».

**Входит:**

- приём покупок из автоматизации iOS «Транзакция» (Команды, iOS 17+);
- очередь «Входящие» с подтверждением одним тапом;
- запоминание «карта → счёт» и «продавец → категория» (правила, без ИИ — как в чеках);
- три пути подтверждения: мой расход / оплатил за других / в общие расходы;
- защита от дублей (в т.ч. с уже введёнными вручную расходами).

**Не входит (сознательно):**

- FinanceKit — только Apple Card/Cash/Savings (США) и банки UK, нужен нативный app; к Kaspi/Halyk
  не применим;
- онлайн-оплаты Apple Pay и оплата пластиком — Wallet-автоматизация их не видит. Это не баг;
- доходы, переводы, возвраты — автоматизация срабатывает только на оплату;
- автоматическая запись без подтверждения — **отказались** (решение 24.11.2026): каждую покупку
  пользователь подтверждает сам.

## 2. Как это работает (поток)

```text
iPhone: оплата в Wallet
  └─ Команды → автоматизация «Транзакция» (запуск сразу, без вопроса)
       └─ POST https://<project>.supabase.co/functions/v1/wallet-ingest
            Authorization: Bearer <личный ключ>
            { amount, merchant, card, name, occurred_at, tz, v }
                 └─ Edge Function: ключ → user_id → разбор суммы → INSERT wallet_inbox (pending)
                      └─ ответ { id, message } (команда может показать уведомление)

CashFlow (при открытии / возврате на вкладку)
  └─ загрузка wallet_inbox where status = 'pending' → бейдж «Новые покупки · N» на Главной
       └─ «Входящие» → карточка покупки → один из путей §6
            └─ транзакция сохраняется ОБЫЧНЫМ путём (save_tx / save_shared_entry)
                 с полем wallet_inbox_id → триггер в той же транзакции БД закрывает строку очереди
```

Ключевые решения:

1. **Функция ничего не считает и не трогает балансы.** `save_tx` принимает `p_new_balance`,
   посчитанный клиентом; сервер, записав баланс сам, гонялся бы с открытыми вкладками (та же
   проблема, что решали дельтой в v32). Поэтому сервер пишет только черновик.
2. **Очередь закрывается в той же транзакции БД, что и запись расхода** — через колонку
   `transactions.wallet_inbox_id` и триггер (§4.4). Ни один путь сохранения не может оставить
   «расход записан, а покупка всё ещё во Входящих», и две вкладки не запишут одну покупку дважды
   (уникальный индекс).
3. **Новые формы не пишем.** Все три пути — существующие `TxPage`, `SharedEntryFormPage`,
   `SharedPurchaseFormPage` с новым пропом-префиллом `fromInbox`.

## 3. Что отдаёт автоматизация iOS (и как с этим жить)

Поля входа команды (по отчётам сообщества, официальной таблицы у Apple нет):
`Amount`, `Merchant`, `Card` (название карты в Wallet), `Name`, плюс `Transaction` целиком.

Известные особенности — каждую обрабатываем явно:

| Особенность | Что делаем |
| --- | --- |
| `Merchant` иногда пустой | Строка всё равно сохраняется; на карточке «Без названия», категорию выбирает пользователь |
| `Amount` иногда `0` / пустой | Строка сохраняется с `amount = null` → «Сумма не пришла», поле суммы в фокусе |
| Сумма — строка с форматированием локали: `1 234,50 ₸`, `₸1,234.50`, `$12.99`, `12,99 €`, NBSP | Разбор на сервере (§5.3), сырая строка хранится в `raw` |
| Валюты в поле может не быть | Валюта = валюта счёта, привязанного к карте |
| Тайм-ауты автоматизации | Функция отвечает быстро: один INSERT, без внешних запросов |
| Нет ID транзакции Wallet | Дубли — мягкой подсказкой (§7), не жёстким отказом |
| Нет сети в момент оплаты | Покупка теряется; закрывается дублями/ручным вводом. Офлайн-буфер в команде — этап 9 (необязательный) |
| Срабатывает только на телефоне, где карта | Ключ на каждое устройство (iPhone, Watch идёт через iPhone) |

Почему не открываем приложение из команды: `Open URL` на iOS открывает Safari, а не PWA с экрана
«Домой» — пользователь окажется в другом окне без сессии. Только уведомление.

## 4. Схема БД (миграция v41, `supabase/migrations/<ts>_v41_wallet_inbox.sql`)

Все новые таблицы — по правилам v36: `user_id`, индекс, политика `owner`, триггеры
`tenant_owner` + `tenant_refs` (ссылки на свои строки). Сервисная запись (service_role) обязана
передать `user_id` явно — без него NOT NULL, это намеренно.

### 4.1 `api_tokens` — личные ключи для команды

| Колонка | Тип | Смысл |
| --- | --- | --- |
| `id` | text PK | |
| `user_id` | uuid | владелец |
| `name` | text not null | «iPhone», «Watch» — вводит пользователь |
| `token_hash` | text unique not null | SHA-256(hex) ключа; сам ключ не хранится |
| `prefix` | text not null | первые 6 символов для отображения «cf_a1b2c3…» |
| `scope` | text not null default 'wallet_ingest' | CHECK — на будущее (другие интеграции), ключ ничего больше не умеет |
| `created_at`, `last_used_at`, `revoked_at` | timestamptz | `last_used_at` — «последний сигнал» в настройках |

- Ключ: `cf_` + 32 байта `gen_random_bytes` в base64url. Случайный 256-битный ключ → простой
  SHA-256 достаточно (HMAC с секретом, как у OTP, тут не нужен: перебор невозможен).
- RPC `issue_api_token(p_name text) returns text` — создаёт строку и **один раз** возвращает ключ.
- RPC `revoke_api_token(p_id text)` — ставит `revoked_at`.
- Клиент `select` видит только `id, name, prefix, scope, created_at, last_used_at, revoked_at`
  (`token_hash` — `REVOKE SELECT (token_hash)` у authenticated).
- Лимит: не больше 10 активных ключей на пользователя (`issue_api_token` → `too_many_tokens`).

### 4.2 `wallet_inbox` — очередь покупок

| Колонка | Тип | Смысл |
| --- | --- | --- |
| `id` | text PK | |
| `user_id` | uuid | |
| `token_id` | text → api_tokens ON DELETE SET NULL | с какого устройства |
| `status` | text not null default 'pending' | CHECK `pending / confirmed / dismissed / duplicate` |
| `amount` | numeric null | null — сумма не пришла/не разобрана |
| `currency` | text null | null — не указана, берём валюту счёта |
| `merchant` | text not null default '' | как пришло (≤ 200 симв.) |
| `merchant_key` | text not null default '' | нормализованный ключ (§5.4) |
| `card_label` | text not null default '' | название карты в Wallet (≤ 100) |
| `occurred_at` | timestamptz not null | время с телефона; нет/кривое → время приёма |
| `received_at` | timestamptz default now() | |
| `raw` | jsonb not null | тело запроса как есть (отладка новых форматов сумм) |
| `transaction_id` | text → transactions ON DELETE SET NULL | чем закрыта |
| `resolved_at` | timestamptz | |

Индексы: `(user_id, status, occurred_at desc)`; CHECK `jsonb_typeof(raw) = 'object'`,
`octet_length(raw::text) <= 4096`.

Хранение: `confirmed/dismissed/duplicate` старше 90 дней удаляются при приёме новой покупки
(как строки OTP старше суток — без cron). `pending` не удаляются никогда.

### 4.3 Правила сопоставления

**`wallet_cards`** — карта → счёт: `id`, `user_id`, `card_label` (unique с user_id),
`account_id → accounts ON DELETE CASCADE`. Нет строки → на карточке «Какой это счёт?».

**`wallet_merchants`** — продавец → категория: `id`, `user_id`, `merchant_key` (unique с user_id),
`category_id → exp_categories ON DELETE CASCADE`, `uses int`, `last_used_at`.
Пишется **только из подтверждения пользователя** (последний выбор побеждает) — upsert внутри
триггера §4.4, то есть ровно тогда, когда расход реально записан.

### 4.4 Закрытие очереди: `transactions.wallet_inbox_id` + триггер

- `ALTER TABLE transactions ADD COLUMN wallet_inbox_id text REFERENCES wallet_inbox ON DELETE SET NULL`
- `CREATE UNIQUE INDEX ... ON transactions (wallet_inbox_id) WHERE wallet_inbox_id IS NOT NULL` —
  одна покупка → одна транзакция (вторая вкладка получит 23505 → «Эта покупка уже записана»).
- `tenant_refs` для transactions: + `wallet_inbox_id → wallet_inbox`.
- Триггер `wallet_inbox_resolve` AFTER INSERT OR UPDATE OF wallet_inbox_id ON transactions:
  - строка очереди не `pending` → `RAISE 'inbox_already_resolved'` (вся запись откатывается);
  - иначе `status = 'confirmed'` (или значение из `p.inbox_status = 'duplicate'` — см. ниже),
    `transaction_id`, `resolved_at`;
  - upsert `wallet_cards(card_label → account_id)` и `wallet_merchants(merchant_key → category_id)`
    если у строки есть `card_label` / `merchant_key`.
- `save_tx` — новая версия с той же сигнатурой: в INSERT добавляется
  `wallet_inbox_id = nullif(p_tx->>'wallet_inbox_id','')`, в `ON CONFLICT DO UPDATE` колонка
  **не перезаписывается** (правка транзакции не отвязывает покупку). Старый фронт поле не шлёт —
  совместимо.
- `save_shared_entry` — новая версия (копия актуальной v32 + одна колонка в двух INSERT в
  `transactions`). Не забыть: старая функция молча отбросит поле — проверка схемы на клиенте как
  `sharedSchema.fees` (§9).
- RPC `link_inbox_tx(p jsonb {inbox_id, transaction_id})` — «Уже записано»: ставит
  `wallet_inbox_id` существующей транзакции (если у неё нет своего) → тот же триггер, статус
  `duplicate`. Баланс не трогает.
- RPC `dismiss_inbox(p jsonb {ids})` — «Не записывать»: только `pending` → `dismissed`.
- Удаление транзакции → `wallet_inbox.transaction_id` = NULL, статус остаётся `confirmed`
  (пользователь удалил сознательно; покупка не воскресает во Входящих).

### 4.5 Приём: RPC `wallet_ingest(p jsonb)` (только service_role)

`SECURITY DEFINER`, `REVOKE EXECUTE` у anon/authenticated. Делает всё одной транзакцией:

1. ключ по `token_hash` (не отозван) → `user_id`, `token_id`; нет → `invalid_token`;
2. лимит: ≤ `p.max_per_hour` строк на ключ за час (под `FOR UPDATE` строки ключа) → `too_many`;
3. INSERT `wallet_inbox` (+ уборка старше 90 дней), `last_used_at = now()`;
4. возвращает `{id, account_id, category_id}` по правилам — функция формирует текст уведомления.

## 5. Edge Function `wallet-ingest`

Структура как у `receipt-proxy`/`auth-otp`: `handler.ts` на Web API (проверяется в Node без
Supabase CLI, зависимости внедряются), `index.ts` — Deno. `make fn-deploy name=wallet-ingest`,
в Makefile `FN_FLAGS_wallet-ingest := --no-verify-jwt` (ключ свой, JWT у команды нет).

### 5.1 Контракт

`POST /functions/v1/wallet-ingest`, `Authorization: Bearer cf_…`, `Content-Type: application/json`

```json
{ "v": 1, "amount": "1 234,50 ₸", "merchant": "MAGNUM CASH&CARRY", "card": "Kaspi Gold",
  "name": "", "occurred_at": "2026-11-24T19:05:12+05:00", "tz": "Asia/Almaty" }
```

| Ответ | Когда |
| --- | --- |
| 200 `{id, message}` | принято (`message`: «2 500 ₸ · Magnum → Kaspi Gold · подтвердить в CashFlow») |
| 400 `bad_request` | не JSON, тело > 4 КБ, `v` неизвестна |
| 401 `invalid_token` | нет/неверный/отозванный ключ — одинаково, без подробностей |
| 429 `too_many` + `retry_after` | лимит ключа |
| 500 `internal` | остальное; в логах — без ключа и с маской продавца не нужно (это не ПДн), ключ — только `prefix` |

`v` — версия формата команды: новая версия команды → новый разборщик, старые команды продолжают
работать.

### 5.2 Настройки (`DEFAULT_CONFIG`, переопределяются `supabase secrets set`)

`WALLET_MAX_PER_HOUR` (60), `WALLET_MAX_BODY_BYTES` (4096), `WALLET_RETENTION_DAYS` (90),
`WALLET_MERCHANT_MAX` (200). Без деплоя фронта.

### 5.3 Разбор суммы — `_shared/parseAmount.ts` (чистая функция, общая для сервера и тестов)

- убрать NBSP/узкие пробелы, найти символ/код валюты (таблица символов из того же справочника,
  что `constants` валют на фронте — **один источник**: вынести в `src/constants/currencies.json`
  и импортировать в обоих местах; символы `₸ $ € ₽ £ ¥ ₺ ₩ …` и коды ISO);
- десятичный разделитель — последний из `,`/`.`, если после него 1–2 цифры; иначе это
  разделитель тысяч (`1,234` → 1234, `1.234,5` → 1234.5, `12,99` → 12.99);
- `≤ 0`, NaN, > 1e9 → `amount = null` (строка всё равно сохраняется);
- отрицательная/«возврат» — не бывает в этом триггере; если пришло — `null` и `raw` для разбора.

Тесты — таблица из ≥ 30 реальных форм записи (русская, казахская, английская локали iOS).

### 5.4 Нормализация продавца — `merchantKey()` (общая)

lower-case → `ё→е` → убрать кавычки и `ТОО/ИП/LLP/LLC/TOO` → схлопнуть пробелы →
обрезать хвост-номер точки/терминала (`MAGNUM 0123` → `magnum`). Никакого «умного» слияния:
разные ключи — пользователь один раз выберет категорию, дальше правило запомнится.

## 6. Подтверждение: три пути (включая «оплатил за всех»)

Карточка покупки во «Входящих» (`BottomSheet`): сумма (редактируемая; пустая → в фокусе),
счёт (`AccSelect`, подставлен по карте), категория (`CategoryPicker`, по продавцу), дата/время,
заметка = продавец. Внизу — одна главная кнопка и ряд второстепенных:

```text
[            Записать            ]          ← мой расход, путь 6.1
 Оплатил за других · В общие расходы         ← пути 6.2 и 6.3
 Уже записано · Не записывать               ← §7
```

Одно главное действие на экране (как в формах общих расходов: остальное — в шторке).

### 6.1 «Записать» — мой расход

**Валютная покупка** (валютные карты есть — решение 24.11.2026; плюс тенговая карта за границей):
Wallet отдаёт сумму в валюте покупки (`12,99 $`). Транзакция пишется **в валюте счёта** — так
устроены `transactions` и `TxPage` (баланс += сумма как есть, без пересчёта). Поэтому:

- `item.currency` есть и ≠ валюте счёта → на карточке обязательное поле «Списалось со счёта, ₸»
  (как «Сколько списалось со счёта» в общих расходах, §5.18); «≈ по курсу» — только по тапу
  (`ratesFromAccounts`), молча не подставляется; «Записать» без него недоступна;
- исходная сумма уходит в заметку: «Apple · 12,99 $» (видно в истории, ищется);
- валюта = валюте счёта → поле не показывается;
- `currency` не пришла → считаем валютой счёта (подпись «валюта не указана — как у счёта»).
Тот же расчёт — для путей 6.2 и 6.3 (в формах общих расходов поле уже есть).

Быстрый путь без открытия формы: собирает tx как `TxPage` (тот же хелпер расчёта баланса —
**вынести** из `TxPage` в `utils/txSave.js`, а не копировать) → `save_tx` с `wallet_inbox_id`.
`useSave`, ошибка над кнопкой. Нужен чек/заметка подробнее → «Подробнее» открывает `TxPage`
с префиллом (тот же `fromInbox`).

### 6.2 ~~«Оплатил за других» через TxPage~~ — отменено (24.11.2026)

У нового расхода тугла «Оплатил за других» нет сознательно (коммит `546dc75`, тест
`TxPageSplit`): делить с друзьями — только через «Общие расходы». Разовое «заплатил за пару
человек» = новая туса в пути 6.3. Описание ниже оставлено для истории решения.

#### (было) «Оплатил за других» — расход с долгами людям (без группы)

Когда: заплатил за пару человек разово, группа не нужна.
Открывается `TxPage` с `prefill = fromInbox` и включённым `SplitToggle` (`initialSplitOn`).
Дальше — существующая логика: моя доля в статистике, остальное → `debt_events` людям.
`wallet_inbox_id` уходит в `save_tx` → очередь закрывается.

⚠️ `TxPage` пишет `save_tx` и `debt_events` двумя вызовами (не атомарно — существующее
поведение). Очередь закрывается вместе с `save_tx`; если `debt_events` упадёт — пользователь
увидит ошибку формы, как сейчас. Новую неатомарность не добавляем; перевод сплита на RPC —
отдельная задача вне этой фичи.

### 6.3 «В общие расходы» — оплатил за всех в тусе/Tricount

Шторка выбора группы:

- активные группы (не архив), сверху — с последней активностью; рядом тип: «Туса» / «Tricount»;
- первая строка — «＋ Новая туса» (группа создаётся вместе со счётом, как сейчас);
- если по этому `merchant_key` раньше уже выбирали группу за последние 12 часов — она
  предложена первой (туса идёт вечер: кафе → такси → бар). Только подсказка в сортировке,
  не автоматический выбор.

Дальше — роутер по `group.mode` (как `editSharedEntryScreen`, не ветки внутри форм):

| Группа | Экран | Префилл | Зафиксировано |
| --- | --- | --- | --- |
| Туса (`event`) или новая | `SharedEntryFormPage` | сумма, валюта, счёт, категория, дата, название = продавец | «Платил: Я» (оплатил я с телефона), счёт списания |
| Tricount (`mirror`) | `SharedPurchaseFormPage` | то же | «Платил: Я» |

- Префилл — новый проп `fromInbox` (объект строки очереди), **не** `linkTx`: `linkTx` означает
  «транзакция уже есть, не создавать», а здесь транзакции ещё нет — форма создаёт её сама в
  `save_shared_entry`, как обычный счёт. Смешивать нельзя: удаление записи с `linked_tx_snapshot`
  не удалит транзакцию.
- `sharedSave.js` (`buildBillSave` и аналог для покупки) кладёт `wallet_inbox_id` в объект
  транзакции. Очередь закрывается в той же транзакции БД, что и счёт, доли и балансы.
- Черновик формы (`useFormDraft`) — ключ `shared.draft.inbox.<inboxId>`: ушёл с формы — покупка
  остаётся во Входящих, черновик подхватится при повторном входе с той же покупки.
- Валюта: Wallet отдаёт сумму в валюте покупки. Если она ≠ валюте счёта — работает существующее
  «Сколько списалось со счёта» (§5.18 общих расходов), молча не угадываем.
- Доплата с другого счёта / разные карты — существующий «Доплатил с другого счёта» (`copyFrom`).

## 10. Безопасность

- Ключ умеет **только добавить строку во Входящие**: не читает данные, не трогает балансы.
  Утёк ключ — худшее последствие: мусор во Входящих; лечится «Отозвать».
- В БД — только SHA-256; в логах — только `prefix`; в ответах 401 — без причины.
- Функция работает от service_role, но всё делает через один `SECURITY DEFINER` RPC
  (`wallet_ingest`), который сам проверяет ключ, — никаких прямых `insert` с service_role в коде.
- Ограничения размера тела/полей, лимит в час на ключ, CHECK на `raw`.
- Ключ не вшивается в iCloud-ссылку команды (ссылка публичная) — только «вопрос при импорте».

## 13. Принятые решения

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Источник данных | Автоматизация «Транзакция» в Командах | Единственный способ для PWA и банков РК |
| Запись на сервере | Только черновик во Входящие | Баланс считает клиент; серверная запись гонялась бы со вкладками |
| Закрытие очереди | `transactions.wallet_inbox_id` + триггер + уникальный индекс | Атомарно для любого пути записи, без дублей |
| Категория | Правило «продавец → категория» из последнего подтверждения | Без ИИ — как в чеках |
| Оплатил за всех | Отдельный путь в существующие формы групп с `fromInbox` | Не дублировать логику долей/долгов/балансов |
| `fromInbox` vs `linkTx` | Разные пропы | `linkTx` = транзакция уже есть; смешивание ломает удаление |
| Дубли от команды | Мягкая подсказка, не отказ | Нет ID Wallet; одинаковые покупки подряд реальны |
| Ключ | Свой, SHA-256, только scope `wallet_ingest` | JWT живёт час; ключ с минимальными правами |
| Открытие приложения из команды | Нет, только уведомление | iOS откроет Safari, а не PWA |
| Уведомление команды (24.11) | Только при проблеме: нет суммы / карта не привязана; и при проверке связи | Меньше шума; решает сервер (`notify`), команду менять не нужно |
| Валютные карты (24.11) | Есть → поле «Списалось со счёта» обязательно при валюте ≠ счёта | Транзакция — в валюте счёта, курс банка ≠ `avg_rate` |
| Автозапись (24.11) | Нет — подтверждение каждой покупки | Решение пользователя |
| Справочник валют | `_shared/currencies.json` — один для фронта и функций | Deno не импортирует из `src/`, Vite из `supabase/` — может |
| Лимит тела | 2048 байт (≤ ½ CHECK `raw`) | jsonb-текст длиннее исходного JSON |
| «US$» и символы с буквой | Псевдоним `US$`; символ — только без буквы перед ним | Иначе «US$5» распознавался как сингапурский «S$» (поймал тест) |

## 16. Команда iOS «CashFlow: покупка» (v1)

### Готовая команда (основной путь, 25.11.2026)

`make shortcut` → `scripts/build-wallet-shortcut.mjs` собирает команду (plist), подписывает
`shortcuts sign --mode anyone` (macOS, вход в iCloud) и кладёт в `public/cashflow-purchase.shortcut`.
Ключа в файле нет — «вопрос при импорте». Адрес функции — из `REACT_APP_SUPABASE_URL` (`.env`).
Экран «Apple Pay» → «Установить команду» ведёт на этот файл (`WALLET_SHORTCUT_URL`; Vercel отдаёт
его скачиванием, без кэша — `vercel.json`). Пересобирать — только если меняется формат или адрес.

Что делает команда: «Текст» (ключ) → «Получить содержимое URL» (POST JSON: `amount`, `merchant`,
`card`, `name` — свойства входа; `input` — вход целиком текстом) → «Получить значение» `alert` →
«Если» есть значение → «Показать уведомление». Без «Если/Иначе» для проверки связи: запрос без
полей сервер считает проверкой (`handler.ts`). Показывать ли уведомление — решает сервер (`alert`),
в т.ч. при ошибках (неверный ключ, лимит) — команда HTTP-коды не различает.

⚠️ Имена свойств входа (`Amount`, `Merchant`, `Card`, `Name`) Apple не документирует. Не совпало —
поле придёт пустым, покупка попадёт во «Входящие» с «сумма не пришла», а в `wallet_inbox.raw.input`
будет видно, что прислал iOS, — по нему поправить `FIELDS` в скрипте и пересобрать.

### Что сделать пользователю

1. CashFlow → Меню → Apple Pay → «Создать ключ» → «Скопировать».
2. «Установить команду» → «Добавить команду» → вставить ключ.
3. «Команды» → «Автоматизация» → ＋ → «Транзакция» → все карты → «Запускать сразу» → «CashFlow:
   покупка». (Автоматизацию файлом не поставить — только руками, это 5 нажатий.)
4. Запустить команду вручную → «Связь с CashFlow есть ✅».

### Запасной путь — собрать вручную

Шаги — на экране «Apple Pay» («Не открывается — собрать вручную», `SHORTCUT_STEPS`).

**Ключ без экрана** (если приложение недоступно) — выдать вручную, он покажется один раз:
`make db-query sql="select set_config('request.jwt.claims', json_build_object('sub', (select id from auth.users where email = '<почта>'))::text, false); select issue_api_token('iPhone');"`
(два оператора: claims выставляются раньше, чем `issue_api_token` читает `auth.uid()`; проверено).
